## N1【P3 · 规则写入缓冲放大 + 读写口径对齐】

- **位置**：外壳 main.c on_rule_add（写侧）+ 规则列表刷新 / on_rule_sel（读侧×2）
- **报告原述**：img 源最长 4096 WCHAR，UTF-8 可达 12288 字节，imgc 只有 1024
  字节 → 超长中文名（约 341 字以上）被静默截断，规则指向不存在的图片；
  写侧 1024【字节】/ 读侧 1024【个 WCHAR】口径不对称。
- **核验补充（报告未算到的关键事实）**：img 来自 FindFirstFile 枚举的**文件名**，
  NTFS 单文件名上限 255 字符——按 UTF-8 最坏 4 字节/字符 = 1020 字节 + NUL
  = 1021 ≤ 1024，**合法文件名实际装得下，截断路径对合法输入触发不了**。
  本条的真实身份是"魔法数字 1024 贴着理论边界、无余量注释"的脆弱写法。
- **修复**：
  - 写侧 `imgc[1024]` → `imgc[12288]`（含上述边界分析注释）；
  - 读侧两处 `char img[1024]` → `[12288]`、`WCHAR imgw[1024]` → `[4096]`，
    与写侧口径对齐（否则放大写侧后又产生"写得进、读不满"的新不对称）；
  - 放大不产生超长 ini 行：合法文件名 ≤255 字符，实际写入值 ≤1020 字节，
    ini 行缓冲（4096 字符）不会因此受压。

## N2【P3 · 钩子防御】MyFillRect：lprc 判空

- **位置**：DLL dllmain.cpp MyFillRect
- **问题**：FillRect 契约要求 lprc 非空，但本函数是全局钩子，若某调用方违规
  传 NULL 且原函数在该路径只是返回 0，紧接的 `lprc->left` 就是 DLL 新引入的
  解引用崩溃点。
- **修复**：`if (savedDC)` → `if (savedDC && lprc)`——钩子要比原函数更保守。

## N3【设计取舍 · 知悉即可，未改动】

BitmapGDI 常驻图片完整原始字节，图集总内存无总量上限（N 张图 = N × 文件大小）。
有单文件 256MB 上限 + bad_alloc 兜底，不崩只是占内存。维持现状：加总量软上限
会拒绝加载或强制按需解码，后者牺牲线程安全模型，得不偿失；留给未来真遇到
内存压力时再议。
