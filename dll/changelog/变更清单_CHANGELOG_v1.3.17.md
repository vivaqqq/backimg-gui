### 1.1 源图缓存泄漏（审计 #1）

**根因**：`ScaleCache` 里有两个容器——`m_items`（缩放结果）受 32MB LRU 预算约束，
`m_sources`（每线程解码的源位图）按 ownerId 存且**完全没有预算**；
`Drop()` 只清 `m_items`。于是每次换图/换目录，旧 ownerId 的源位图永久驻留。

**修法**（两层）：
1. `m_sources` 改按**文件内容哈希**为键：同一份内容重建列表时直接命中缓存，零增长；
   内容变了由 LRU 预算淘汰。
2. 加硬上界：单线程源图缓存 ≤ 64MB 且 ≤ 16 条，超出按 LRU `delete`。

**实测**（用户 39 张 1024×1536 PNG）：

| 指标 | v1.3.16 | v1.3.17 |
|---|---|---|
| 缩放一遍 | +280 MB | +166 MB |
| 列表析构后残留 | **+177 MB** | **+66 MB（有界）** |
| 重建 5 次 | 线性增长到 +885 MB | **每轮 +0 MB** |

### 1.2 Size 未初始化（审计 #2）

- `SIZE Size = { 0, 0 };` 加初值；
- 新增 `IsValid()`：只有"图片头解析确证结构完整"或"GDI+ 探测状态 Ok"时才为真；
- `dllmain.cpp` 的过滤恢复为 `bmp->IsValid()`（v1.3.16 退化成了裸比较 `Size.cx > 0`）。

**实测**：构造不存在的文件 200 次，垃圾值 200/200 → **0/200**。

### 1.3 无限重绘（审计 #3）

把 `t_myData.size = wndSize;` 提到所有提前 return 之前（先取旧值比较，再立刻写回）。
正常路径仍收敛到 1 次；`imageList` 为空 / `GetScaled` 失败从 1000/1000 次降到 **1 次**。

### 1.4 GDI+ 串行锁（审计 #4）

`GdiplusMutex()` 真正接上，覆盖全部 GDI+ 调用点：解码（`FromStream`）、
`DrawImage`、`GetHBITMAP`、GDI+ 对象 `delete`。锁用"故意泄漏的单例"，
避免与 thread_local 析构顺序打架。缓存查找与 GDI 句柄操作在锁外。

### 1.5 mode 5 语义说明（审计 #5）

mode 5 的语义变化是 v1.3.16 按需求改的（等比、不变形），
但 GUI 没把"相对 v1.3.15 拉伸填满"这一点说清。现在行为说明写明：

> 「缩放」= 整图完整适配（四周可能留白）；「缩放并填充」= 等比铺满并裁掉溢出。

### 1.6 自检程序可复现（审计 #9）

- 去掉对缺失 `probe/veh.h` 的依赖（改为自带 `crashlog.h`）；
- 输出路径改相对当前目录；
- 图片路径一律走命令行参数（Windows argv 是 ANSI 码页，用 `CP_ACP` 转宽字符）；
- 新增 `运行自检.cmd` 一键跑全部自检。

## 二、v1.3.17 新发现并修复的问题（审计报告之外）

### 2.1 🔴 MinGW `thread_local` 析构崩溃雷（比审计所有问题都严重）

**现象**：`static thread_local ScaleCache g_threadCache;`（内含 `std::vector`）在线程退出时，
TLS 析构回调跑在**已被释放、被 ucrt 填成 0xEE 的内存**上 → 二次释放 → 崩溃。

gdb 实测崩溃栈：
```
ntdll!RtlExitUserThread → tls_callback → run_dtor_list
  → ScaleCache::~ScaleCache → vector::~vector → _M_deallocate
被 free 的指针 = 0xfeeefeeefeeefeee
```

**独立最小复现**（与 GDI+ 无关）：`thread_local` 里放 `std::vector` 必崩；
只放 `int` 则 200 轮全过。析构日志打印出的 size/capacity 全是垃圾值。

**为什么 v1.3.15/v1.3.16 没暴露**：v1.3.16 的另一个 `thread_local MyData` 全是 POD
没有析构函数；而当年那句"40/40 零崩溃"其实是**压测装了 VEH 异常处理器，
把崩溃吞掉了**——假象。

**修法**：`thread_local` 只存**裸指针**（平凡析构，不注册 TLS 回调），
缓存对象堆上分配并登记到全局表；窗口销毁时（`MyDestroyWindow`）主动释放本线程缓存，
DLL 卸载时兜底释放全部。

### 2.2 🟠 GDI 句柄耗尽（线程退出不释放缓存）

修掉 2.1 之后暴露：每线程缓存在线程退出时不再被析构（也不该靠析构），
压测里句柄 2583 → 5161 → 7739 → **9999 撞上限**，之后 `CreateCompatibleDC` 失败、背景画不出。

**修法**：新增**死线程缓存清扫**——登记表记录每个缓存的属主线程 id，
定期检查属主线程是否已退出（`GetExitCodeThread` == STILL_ACTIVE 判活），
已退出的连缓存一起释放。实测句柄从单调增长变为 **655~1959 稳定波动**。

> 踩坑记录：判活一开始用 `WaitForSingleObject(h,0)==WAIT_TIMEOUT`，
> 但**当前线程等自己会立即返回 WAIT_OBJECT_0**，把活着的自己误判成已死，
> 清扫直接删了正在使用的缓存 → 堆损坏 → `abort()`（且 abort 走 raise()，
> 不经过 VEH，崩溃记录器里什么都看不到）。改为 `GetExitCodeThread` + 当前线程直通。

> 踩坑记录 2：清扫最初放在 `GetThreadCache()` 里，而它在 `GetScaled` 里
> **持 GDI+ 锁期间**被调用 → 清扫 delete 缓存 → `~ScaleCache` 再拿同一把锁
> → `std::mutex` 不可重入 → **自我死锁**（表现为压测挂死而非崩溃）。
> 已把清扫移到拿锁之前。

### 2.3 🟡 损坏图片直送 GDI+ 的新暴露面

v1.3.15 恰好在 `SHCreateMemStream` 之前就 `delete[]` 缓冲区，GDI+ 读到的是被
free-list 元数据污染的首字节，PNG 签名被破坏后 GDI+ 提前安全退出——
"歪打正着"的保护。v1.3.16 保留完整字节，损坏 PNG 会被真正解析。

**修法**：新增 `ImageHeader.h` 轻量图片头解析（PNG 块走查 + IHDR CRC 校验、
JPEG SOI/EOI/SOF）。**核心准则是"绝不单独否决"**——只有能证明"确证损坏"
（块越界 = 截断、IHDR 长度/CRC 不对、尺寸离谱）才拒绝；
看不懂的一律交 GDI+ 裁决，避免错杀。

> 踩坑记录：第一版写死"最多 64 个 PNG 块"，把用户一张带 212 个 IDAT 块的
> 合法 PNG 误判成损坏。已去掉数量上限（循环每轮至少前进 12 字节且块长已做
> 越界校验，天然不会跑飞），并加回归测试锁住。
